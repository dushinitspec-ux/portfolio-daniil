<Section id="problem">

Fragt man ein kleines Hotel oder Büro, was an seinem Netzwerk hängt, lautet die ehrliche Antwort
meist: „Wissen wir nicht." Kameras, Rekorder, Drucker, Access Points und der PC, den jemand vor
Jahren für den Fernsupport eingerichtet hat, hängen alle im selben flachen Netz. Ein neues Gerät
bemerkt niemand, und niemand weiß, dass eine Kamera nach dem Zurücksetzen auf Telnet antwortet.

Die NIS2-Richtlinie der EU nennt das Management von Assets unter den Mindestmaßnahmen der
Cybersicherheit (Artikel 21 Absatz 2 Buchstabe i). Sie gilt für mittlere und große Unternehmen
bestimmter Sektoren, viele kleine Betriebe fallen also nicht darunter. Eine Liste dessen, was im
Netz ist, bleibt trotzdem der erste Schritt jeder Sicherheitsarbeit. Dieses Werkzeug hilft, sie zu
führen; NIS2-konform macht es allein niemanden.

</Section>

<Section id="solution">

- Die zu scannenden Netze müssen ausdrücklich angegeben werden. Erlaubt sind nur private Adressbereiche, nichts größer als /22, und das Werkzeug meldet sich nirgends an und nutzt keine Lücken aus.
- Ein Scan pingt alle Adressen mit asyncio **parallel** an und liest dann die ARP-Tabelle des Betriebssystems für die MAC-Adressen. So taucht auch ein PC auf, der Pings verwirft.
- Jedes erreichbare Gerät bekommt eine TCP-Verbindung zu einer kurzen Portliste (Telnet, FTP, RDP, SMB, RTSP, Winbox…) und eine Reverse-DNS-Abfrage für seinen Namen.
- Aus der MAC-Adresse ergibt sich der Hersteller, aus einem kleinen mitgelieferten Auszug der IEEE-Liste. Zufällige MACs von Smartphones und virtuellen Maschinen werden als solche markiert, statt einen falschen Hersteller zu bekommen.
- Geräte werden im SQLite-Verzeichnis über ihre MAC verfolgt, eine neue DHCP-Adresse ist also kein neues Gerät. Jeder Scan wird mit dem vorherigen verglichen: neues Gerät, verschwunden, IP geändert, Port geöffnet.
- Ein neues Gerät oder ein neu geöffneter riskanter Port löst eine Telegram-Nachricht pro Scan aus. Die Webseite zeigt das Verzeichnis mit Filtern und die Risiken mit verständlichen Erklärungen und exportiert CSV und JSON.

</Section>

<Section id="stack">

<Stack />

Die Erkennung nutzt die Systembefehle `ping`, `arp -a` und `ip neigh` statt Raw Sockets und
läuft deshalb ohne Administratorrechte. Ihre Ausgabe wird als ASCII dekodiert: Auf einem
russischen Windows werden die Wörter unlesbar, aber `TTL=`, IP- und MAC-Adressen bleiben in jeder
Sprache erhalten — eine Lehre aus dem Uptime Monitor. Geräte zuordnen und Scans vergleichen sind
reine Funktionen, und jeder Scan wird in einer Transaktion gespeichert.

</Section>

<Section id="code">

Der Vergleich zwischen Scans ist eine reine Funktion. Ports werden mit der letzten Sichtung des
Geräts verglichen, auch wenn sie Wochen zurückliegt, und ein Gerät gilt nur als verschwunden,
wenn dieser Scan sein Netz abgedeckt hat:

```python
def diff(*, last_known, previous_scan, current, in_scope):
    changes = []
    for key, now in current.items():
        before = last_known.get(key)
        if before is None:
            changes.append(Change(ChangeKind.NEW, key, tuple(sorted(now.ports)), new_ip=now.ip))
            continue
        if key not in previous_scan:
            changes.append(Change(ChangeKind.RETURNED, key, new_ip=now.ip))
        if before.ip != now.ip:
            changes.append(Change(ChangeKind.IP_CHANGED, key, old_ip=before.ip, new_ip=now.ip))
        if opened := now.ports - before.ports:
            changes.append(Change(ChangeKind.PORT_OPENED, key, tuple(sorted(opened))))
        if closed := before.ports - now.ports:
            changes.append(Change(ChangeKind.PORT_CLOSED, key, tuple(sorted(closed))))

    for key in previous_scan:
        before = last_known.get(key)
        if key not in current and before is not None and in_scope(before.ip):
            changes.append(Change(ChangeKind.GONE, key, old_ip=before.ip))
    return changes
```

<Section id="bug">

### Hostnamen fehlten, wenn viele Adressen keinen Namen hatten

<BugPart id="problem">

Bevor ich Reverse DNS ein ganzes Subnetz anvertraute, habe ich es auf meinem Windows-Rechner
gemessen. Allein wurde `127.0.0.1` in 3 ms zum Rechnernamen aufgelöst. In einem Stapel von 61
Adressen, von denen die anderen 60 keinen Namen haben, kam dieselbe Abfrage leer zurück. In einem
echten Netz heißt das: Geräte verlieren ihre Namen, sobald viele Adressen keinen DNS-Eintrag
haben — und das ist der Normalfall.

</BugPart>

<BugPart id="cause">

Unter Windows schlägt eine Abfrage für eine Adresse ohne Namen erst nach 4,98 Sekunden fehl. Das
Timeout von 2 Sekunden beendete nur das Warten: Ein Thread, der in `getnameinfo` hängt, lässt sich
nicht abbrechen und blieb belegt. Der Platz für parallele Abfragen wurde beim Timeout frei, also
reihten sich neue Abfragen im gemeinsamen Pool hinter belegten Threads ein, und ihre 2 Sekunden
liefen ab, bevor sie überhaupt anfingen.

</BugPart>

<BugPart id="fix">

Reverse DNS hat jetzt einen eigenen Thread-Pool, und ein Platz wird erst frei, wenn der Thread
wirklich fertig ist. `asyncio.shield` verhindert, dass das Timeout das Future abbricht, sonst
würde der Platz wieder zu früh frei. Nach der Korrektur liefert derselbe Stapel den Namen. Ein
Regressionstest stellt das Problem mit einem langsamen Fake-Resolver nach, ganz ohne Netzwerk.

</BugPart>

try:
    name, _ = await asyncio.wait_for(

await self._slots.acquire()
future = loop.run_in_executor(self._pool, self._resolve, ip)
future.add_done_callback(self._release)  # free the slot only when the thread is done
try:
